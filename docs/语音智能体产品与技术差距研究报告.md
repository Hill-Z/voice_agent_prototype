# 语音智能体产品与技术差距研究报告

> 调研日期：2026-09-14  
> 适用范围：产品规划、算法评审、语音运行时与流程引擎研发  
> 说明：本报告基于当前本地原型、项目说明与公开竞品资料。原型中已经存在的页面入口，不等同于后端运行能力已经商用落地。

## 一、结论先行

当前产品已经覆盖机器人配置、话题与流程、工具、RAG、记忆、外呼、回呼、监控、满意度调查和多 Agent 画布等主要入口，产品框架并不缺。真正影响下一阶段竞争力的是六个底层问题：

1. **流程只是“可画”，还不是可靠的对话运行时。** 当前缺少统一的轮次事务、变量生命周期、消费语义、循环保护和 End 后续路由语义，所以客户倾向把所有逻辑继续写进一个大节点。
2. **工具、接口、代码和 MCP 尚未形成统一能力模型。** 现在既有接口、脚本节点、机器人工具和 MCP 配置，但定义分散，权限、入参、返回、超时、审批、版本和审计不能复用。
3. **语音实时链路缺少独立治理。** 打断、话轮结束、多语种混说、噪声和旁人语音不能只靠一个阈值或一个开关，需要统一的音频前处理、说话人判断、语义话轮检测和误打断恢复。
4. **记忆和变量目前偏“字段配置”，没有形成状态治理。** 哪些信息只在本轮有效、何时确认、何时过期、谁能修改、跨 Agent 如何传递，都需要系统规则。
5. **RAG 已有基础召回参数，但离生产知识系统仍有距离。** 缺少摄取与切分质量、权限过滤、重排、引用、失效更新、离线评测和失败回退。
6. **新增方向不能并行铺开。** 最高优先级应是“流程运行时 + 变量实体生命周期 + 工具统一协议 + 语音链路指标”；否则多 Agent、Agent Loop、MCP 和音频原生模型只会把已有不确定性放大。

建议下个月只立 4 个 P0 主题：

| 优先级 | 主题 | 直接结果 |
|---|---|---|
| P0-1 | 对话轮次与流程运行时 2.0 | 四个已知流程问题一次解决，节点真正可拆分 |
| P0-2 | 变量/实体状态中心 | 解决旧值污染、死循环、跨 Agent 传递和可追溯问题 |
| P0-3 | 统一工具协议（接口、代码、MCP） | 所有工具共用参数、权限、执行、错误和审计机制 |
| P0-4 | 语音链路可观测与打断 2.0 | 能量化首包、话轮结束、打断成功、误打断和 ASR 质量 |

Web/App 通话、PolyScore 类质量评分、自动化构建可并行做产品验证；多 Agent、Agent Loop、音频原生模型应先做受控试验，不建议直接替换主运行链路。

## 二、当前产品能力基线

### 2.1 已经具备的产品框架

根据本地原型和项目说明，目前已有：

- 机器人配置、版本、话题、流程与多 Agent 画布；
- 输入变量、会话变量、提取变量和实体配置；
- API、RAG、短信、转人工、回呼、自定义工具，以及代码节点和 MCP 服务配置；
- 问答对、知识发现、向量/混合召回、Top-K 和相似度阈值；
- 客户记忆、客户画像、营销和自动跟进；
- 电话外呼、联系单、回呼计划、通话记录、满意度调查和监控报表；
- 打断灵敏度、强制打断词、工具执行审批、超时和异常兜底等前端配置。

### 2.2 需要警惕的“完成度错觉”

当前大量数据和执行为前端模拟。以流程调试为例，执行器会把节点输出直接合并进一个通用变量对象，并通过模拟条件和随机错误演示运行；变量虽然已经有“跨轮保留”等配置，但没有值版本、确认状态、过期时间、来源轮次和消费记录。工具类型也混合了技术类型与业务预设类型。

因此后续规划应采用三档状态，而不是简单的“有/没有”：

- **已有原型**：有页面和交互，可用于需求验证；
- **已有运行能力**：后端真实执行，具有异常处理和审计；
- **商用可用**：有版本、权限、容量、监控、回退、灰度和验收指标。

## 三、电信行业特定需求与缺口

电信客户不是只需要一个“能接电话的机器人”，而是要求机器人进入运营商的网络、BSS/OSS、工单、计费、身份和合规体系。TM Forum Open API 已将客户账单、产品/服务库存、服务激活、故障单、用量、支付、身份和意图管理标准化；GSMA Open Gateway 还提供号码验证、SIM Swap 等面向运营商网络能力的接口。[1][2]

### 3.1 目前最可能不满足的能力

| 能力域 | 电信客户实际要求 | 当前缺口 | 建议 |
|---|---|---|---|
| 网络接入 | SIP Trunk、多运营商路由、号码池、主被叫显号、DTMF、编解码协商 | 有电话业务页面，但缺少运营商级线路与号码生命周期治理 | 建立“语音通道”资源层，机器人不直接绑定单一线路 |
| 高可用 | 多地域容灾、跨运营商切换、突发并发、限流与降级 | 原型没有容量、路由和灾备模型 | 定义租户/线路/机器人三级并发及自动降级 |
| 话务质量 | 抖动、丢包、RTT、MOS、PDD、静音、ICE/SIP 错误定位 | 当前监控偏业务指标 | 增加“网络—媒体—ASR—LLM—TTS”分段指标；Twilio Voice Insights 已采用此类指标体系。[3] |
| BSS/OSS 集成 | 查账单、套餐、余额、流量、停复机、故障、装维预约、工单 | 目前需要客户逐个自建接口 | 按 TM Forum API 形成电信行业连接器模板 |
| 身份与反诈 | 号码持有人校验、SIM 换卡风险、账户验证、敏感操作二次验证 | 没有电信网络身份能力 | 工具执行前支持风险校验和强认证 |
| 人工协同 | CTI/ACD、队列技能、暖转、屏幕弹屏、上下文传递 | 有转人工配置，但缺少完整传递协议 | 固定交接包：身份、摘要、已完成步骤、待办、关键变量 |
| 合规审计 | 录音告知、隐私脱敏、数据驻留、保存期、可删除、全链路审计 | 有局部脱敏和审批，缺统一策略 | 建立租户级数据政策并强制覆盖机器人配置 |
| 业务连续性 | 外部系统故障时仍可查基础信息、登记工单、稍后补偿 | 只有一般异常兜底 | 引入熔断、幂等、补偿任务和待同步队列 |
| 多语言运营 | 方言、小语种、混说、数字/套餐名/地址准确识别 | 已有多语言选择，但能力随厂商差异大 | 建立“语言 × 厂商 × 电话模型 × 功能”能力矩阵 |

### 3.2 电信版产品不应复制一套机器人

建议通过三层复用支持电信行业：

1. **通用语音智能体平台**：流程、工具、知识、记忆、评测；
2. **电信能力包**：计费、套餐、用量、工单、服务库存、身份校验连接器；
3. **运营商适配层**：SIP、号码、地域、数据驻留、专有 BSS/OSS 字段映射。

这样既能形成行业产品，也不会让核心平台被某一家运营商的字段和流程绑死。

### 3.3 电信行业验收指标

- 线路接通率、PDD、媒体建立成功率、单通话丢包/抖动/RTT/MOS；
- 端到端首句时延、每轮话轮结束时延、打断生效时延；
- 身份验证成功率、敏感操作二次确认率、接口幂等成功率；
- 账单/套餐/用量查询正确率，工单创建与回写一致率；
- 多语言与电话窄带场景分语言 WER、意图准确率、任务完成率；
- 单线路、单租户和全平台的容量及故障切换 RTO/RPO。

## 四、自动化构建：参考 PolyAI Agentic Dialog Platform

PolyAI 的方向不是让模型直接生成一个不可解释的大 Prompt，而是通过 Agent Builder 用自然语言建立 Agent、知识、Talk Tracks 和护栏，再允许测试、分析和迭代；其开发套件支持 IDE、CLI 和 Git。[4][5] Talk Track 将任务拆成步骤，每个步骤只有一个目的和提示，历史步骤 Prompt 不继续进入当前模型上下文；函数负责进入、跳转和退出，并可配验证、重试、API 和路由。[6][7]

### 4.1 我们应该自动生成什么

自动化构建的产物应是**可编辑、可测试、可发布的结构化配置**：

- 机器人角色、目标、限制和开场白；
- 业务范围与意图目录；
- 每个意图对应的短流程或知识回答；
- 节点、边、变量、实体和工具映射；
- 异常、转人工、挂机和安全策略；
- 自动生成的测试集与待确认问题。

不应直接“一句话生成并发布”。所有生成内容先进入草稿，标出以下风险：缺少接口、变量未映射、无退出条件、边条件重叠、隐私字段、破坏性工具和无回退节点。

### 4.2 推荐的自动化构建流程

1. 客户输入业务说明，也可上传现有话术、FAQ、接口文档和流程图；
2. 系统提取目标、用户意图、业务对象、必要字段、工具和限制；
3. 生成“需求理解摘要”，由客户确认，而不是直接生成画布；
4. 按“一个节点只完成一件事”生成流程；
5. 自动匹配已有工具、知识库、变量和实体，未匹配项生成待办；
6. 自动生成正常、歧义、拒绝、接口失败、重复表达和中途换意图测试；
7. 在沙箱运行，显示覆盖率、死路、循环、未初始化变量和工具失败；
8. 人工审批后创建版本并灰度发布。

### 4.3 与 PolyAI 的差距

- 当前有画布和模板，但没有“自然语言需求 → 结构化草稿 → 自动测试 → 人工批准”的完整链路；
- 当前节点内容会存在上下文膨胀风险，尚未明确“只给模型当前步骤 Prompt”的运行语义；
- 缺少对生产对话的持续改进闭环。PolyAI Wren 的公开方向是持续审阅对话、提出修改和生成测试，但业务逻辑变化仍需人工批准。[8]

### 4.4 首期范围

首期只自动生成：单机器人、线性或少量分支流程、变量映射、已有工具引用、异常出口和测试用例。多 Agent 自动拆分、自动修改生产逻辑、自动生成代码工具放到后续，避免一次引入过多不可控因素。

## 五、Web/App 实时通话（WebRTC）

该能力应被定义为新的**会话渠道**，不是另做一套机器人。一个已发布机器人可被电话、网页、App 或 API 会话共同引用。

### 5.1 产品结构

新增“渠道接入”模块：

- 电话：号码/SIP；
- Web：嵌入组件或 JavaScript SDK；
- App：iOS、Android、React Native/Flutter SDK；
- 服务端：WebSocket/WebRTC API。

每个渠道配置品牌外观、麦克风权限文案、欢迎页、自动接听、文本输入、字幕、结束行为和允许的前端工具。机器人提示词、知识、工具、记忆、流程和报表共用。

### 5.2 技术边界

- 前端先向业务后端申请一次性会话令牌，再建立 WebRTC；私有机器人不能把平台密钥下发浏览器。Retell 的 Web Call 和 ElevenLabs 的 Web SDK 都采用短期令牌或后端签发令牌。[9][10]
- WebRTC 负责浏览器/App 的低延迟媒体；服务端仍需要会话鉴权、机器人路由、录音同意、日志和工具执行。
- 处理麦克风拒绝、设备切换、耳机拔出、后台切换、弱网、断线重连、回声、自动增益和音频焦点抢占。
- TURN 不是可选项。企业网络、移动网络和复杂 NAT 下必须准备中继能力。
- 页面/App 会话和电话在分析中保留 `channel` 维度，不能把 Web 通话的质量数据混入运营商线路指标。

### 5.3 可验收结果

- 一次配置可生成 Web 演示链接和嵌入代码；
- Web/App 可与同一机器人通话，通话记录、变量、工具、满意度和评测统一入库；
- 断线可在限定时间内恢复同一会话；
- 令牌不可复用、不可暴露平台密钥；
- 报表能按电话/Web/App 分渠道查看成功率、时延、设备和网络质量。

## 六、统一工具体系：代码、接口、MCP

用户提出的三类是合理的，而且比当前把“回呼、短信、报价、转人工、RAG”等业务用途混在 `type` 字段中更清晰。建议拆成两个维度：

- **实现类型**：接口、代码、MCP；
- **业务分类**：查询、写入、通知、转接、知识、回呼、报价等标签。

ElevenLabs 公开的工具体系也区分 Client、Webhook、Code、MCP 和 System；MCP 还提供服务器级连接、工具列表、测试和逐工具审批模式。[11][12][13]

### 6.1 三类工具的边界

| 类型 | 适用 | 必备配置 | 不适合 |
|---|---|---|---|
| 接口 | 一次 HTTP 调用 | 鉴权引用、请求、参数、返回映射、超时、重试、幂等 | 多步数据加工和复杂分支 |
| 代码 | 计算、格式转换、组合多个 API、轻量业务规则 | 运行语言、依赖/网络白名单、密钥引用、输入输出、资源限制 | 长任务、无限循环、任意系统访问 |
| MCP | 引用第三方或企业 MCP Server 暴露的工具 | Server 连接、协议版本、鉴权、工具同步、启停、审批 | 把远程工具视为天然可信 |

### 6.2 所有工具共用的合同

无论实现类型，必须统一保存：

- 稳定的工具 ID、显示名、模型可见名称、说明和版本；
- JSON Schema 入参和结构化出参；
- 参数来源：模型填写、系统变量、业务变量、固定值；
- 是否只读、是否破坏性、是否幂等、是否访问外部系统；
- 自动执行、客户确认、人工审批或禁用；
- 超时、重试、熔断、并发、去重键和错误映射；
- 对模型返回的简化结果与后台保存的完整原始结果；
- 每次调用的会话、轮次、Agent、版本、入参摘要、结果、耗时和审批记录。

MCP 规范的 `readOnlyHint`、`destructiveHint`、`idempotentHint` 等只能视作提示，不能代替平台自己的信任和审批规则。[14]

### 6.3 兼容策略

- 现有 API 工具迁移为“实现类型=接口”；
- 现有脚本节点可升级为可复用“代码工具”，流程节点只引用工具版本；
- 回呼、短信、转人工仍保留为平台内置工具，但其实现类型由系统管理；
- 现有 MCP 配置迁移为 MCP 连接，连接同步出的每个工具成为统一工具目录中的一项；
- 旧配置只读兼容，新保存时转换为新结构，不要求客户重配。

## 七、Agent Loop：更强推理与时延边界

### 7.1 先纠正目标

“推理更强且响应时长完全不变”不能作为硬承诺。多一步规划、检索或工具调用必然消耗时间。可实现的是：

- 首句可感知时延基本不增加；
- 绝大多数简单问题仍走单步；
- 复杂问题在固定预算内多做 1～2 次检查；
- 超过预算立即降级，不让用户无限等待。

ElevenLabs 已公开用 `interaction_budget` 限制单轮包含推理、工具和重试的总时长；LiveKit 的预生成可以在话轮最终确认前启动 LLM，降低感知时延，但转写变化时结果会被丢弃并重算，增加成本，且不保证每次都降低时延。[15][16]

### 7.2 推荐的“双通道”执行

**快速通道**：明确意图、知识命中、无需工具或单个只读工具，直接生成。  
**推理通道**：多意图、跨工具、低置信度、高风险、结果冲突时进入有界 Agent Loop。

Agent Loop 每次只允许：

1. 判断是否已有足够信息；
2. 选择一个或一组可并行的只读动作；
3. 检查结果是否满足任务；
4. 最多 2 个工具阶段、最多 3 次模型调用、一个总时限；
5. 达到预算后回答已有结果、澄清或转人工。

### 7.3 降低感知时延的方法

- ASR 得到稳定片段后预做意图候选、只读检索和缓存命中；
- 互不依赖的知识和只读接口并行执行；
- 对高频查询缓存“路由结果”和检索结果，不缓存客户敏感写操作；
- 首句只在确实等待工具时给简短自然反馈，避免每轮都说“请稍等”；
- 后置任务（摘要、记忆写入、质量评分）通话后异步执行；
- 流式护栏可与生成并行，但高风险写操作必须阻塞确认。ElevenLabs 的公开说明也明确：并行流式护栏不增加等待，但可能已有少量音频发出；阻塞校验会增加约 200～500ms。[17]

### 7.4 产品配置不应暴露“思考次数”

客户只需要选择：实时优先、均衡、任务优先。后台分别映射时延预算、最大工具阶段和允许的模型。日志展示“选择了什么、调用了什么、为何降级”的简短决策摘要，不保存或展示模型隐式思维链。

## 八、PolyScore 对话质量评分

PolyScore 当前公开方法是：对符合条件的语音通话使用完整转写评分 0～10；六个行为信号归入三类——对话质量 40%、任务成功 40%、客户体验 20%。只有至少 3 个话轮且客户实际参与的语音通话才评分；7～10 为高、4～6 为中、0～3 为低。[18]

它的官方限制同样重要：只看转写，不能验证外部动作是否真的成功，也不了解知识库、流程和预期结果，因此“说得很自信但业务结果错误”仍可能得到高分；官方把它定位为筛查工具，而不是最终结论。[18]

### 8.1 我们不应直接复制一个总分

建议建立“语音对话质量评分”，总分只用于排序，底层保留四个可解释维度：

| 维度 | 建议权重 | 数据来源 |
|---|---:|---|
| 任务结果 | 35% | 流程完成、工具真实返回、外部系统回写、转人工原因 |
| 对话质量 | 25% | 是否理解、是否重复、回答相关性、澄清是否有效 |
| 客户体验 | 20% | 客户情绪变化、打断、沉默、重复表达、满意度 |
| 语音体验 | 20% | ASR 修正、话轮时延、误打断、重叠语音、TTS 可懂度、网络质量 |

### 8.2 两层评分结构

- **确定性事实层**：工具成功、流程是否完成、是否超时、是否转人工、是否重复、时延和网络指标；
- **模型评审层**：理解、表达、礼貌、澄清、上下文连贯和原因解释。

事实层优先，模型不得覆盖事实。例如接口返回失败时，任务成功不得仅因机器人话术流畅而判定成功。

### 8.3 最小产品

- 通话列表增加质量分和“主要问题”；
- 详情展示维度分、证据轮次、确定性指标和模型解释；
- 支持按机器人、版本、语言、渠道、流程节点、工具和时间筛选；
- 人工可修正评分并记录原因，用于校准；
- 每个发布版本都有固定回归集，并观察低分通话是否集中在特定节点。

## 九、多 Agent 架构

当前原型已有 Supervisor/Handoff 和画布，产品入口已经具备，但尚不等于多 Agent 运行时完成。

LiveKit 建议在角色、模型、权限或上下文明显不同的场景拆 Agent，并要求明确传递或总结上下文；ElevenLabs 的 Agent Transfer 则配置目标 Agent、触发条件、转接提示，并明确哪些音频设置继承、哪些提示词/工具/知识不继承。[19][20]

### 9.1 何时值得拆 Agent

- 业务权限不同：查账单与办理停机；
- 知识域不同：销售、技术支持、账务；
- 模型或成本不同：轻量分流、强模型处理复杂问题；
- 话术和合规不同：催收、投诉、未成年人服务；
- 对话阶段不同：身份核验、问题处理、满意度调查。

仅仅因为流程很长，不应自动拆 Agent；能用短步骤 Flow 解决的，优先用 Flow。

### 9.2 必须补齐的运行合同

- 当前唯一负责回复的 `active_agent_id`，避免多个 Agent 同时说话；
- 允许的转接拓扑和最大转接次数，禁止 A↔B 循环；
- 交接包：客户目标、已确认实体、已完成动作、待办、风险、来源 Agent/版本；
- 共享变量白名单，默认不传密码、令牌和无关隐私；
- 上下文策略：完整历史、摘要、只传结构化状态三选一；
- 工具权限按 Agent 授予，Supervisor 不能天然拥有所有业务写权限；
- 转接失败、目标 Agent 不可用、语言/声音不兼容的回退；
- 全会话统一 transcript，同时每条消息和工具调用记录 Agent ID；
- 端到端评测和每个 Agent 的局部评测。

### 9.3 推荐首期架构

采用“一个会话协调器 + 多个专业 Agent”，不要让 Agent 之间任意自由聊天：

- 会话协调器持有音频连接、统一轮次、全局安全策略和状态中心；
- Agent 只拿自己需要的提示、工具和知识；
- Handoff 是原子操作：冻结旧 Agent → 提交交接包 → 激活新 Agent；
- 一次客户话轮最多发生一次 Agent 转接，复杂链路下一轮继续；
- 生产首期限制为树状或有向无环图，明确返回 Supervisor 的唯一出口。

## 十、音频原生端到端模型支持方案

音频原生模型直接处理并生成音频，可利用语气、节奏和情绪，通常减少传统 ASR→LLM→TTS 串行延迟。OpenAI Realtime 支持 WebRTC/WebSocket/SIP 的原生语音到语音；Gemini Live 支持实时音频输入输出、打断、工具和音频转写；Amazon Nova Sonic 将语音理解与生成统一在一个模型中；Hume EVI 还显式使用韵律和情感信号。[21][22][23][24]

### 10.1 不能把原管线直接删除

端到端模型也有明显限制：

- 模型能力和语言支持随版本变化；
- 有的模型不支持结构化输出、代码执行或完整工具能力；
- 音频上下文成本高，长会话需要压缩和重连；
- 精确文字审计、敏感词、数字核验和可复现性更难；
- 音色、发音词典、声音一致性和供应商锁定需要单独验证；
- 实时模型会话通常不能在通话中无缝替换为另一个实时模型。[19][22]

### 10.2 推荐“统一会话接口 + 双引擎”

定义内部统一事件：

- 输入：音频块、用户说话开始/结束、文本、渠道事件；
- 输出：音频块、输出转写、工具调用、打断、错误、用量；
- 状态：listening、thinking、speaking、tool、ended、failed；
- 共同能力：提示词、工具、变量、记忆、知识、护栏和审计。

底层可选择：

1. **级联引擎**：ASR + LLM + TTS，控制强、可替换、适合流程和高合规；
2. **实时音频引擎**：端到端 speech-to-speech，适合开放对话和高自然度；
3. **混合引擎**：音频模型负责话轮和表达，外部文本模型负责高风险推理或工具规划。

机器人页面只显示“语音引擎：标准 / 实时音频（试用）”，高级页面展示能力差异。发生供应商错误、工具不支持或合规校验失败时，下一轮降级到级联引擎；不要在同一段输出中生硬切换声音。

### 10.3 试验与验收

先选 2 个低风险场景进行 A/B：FAQ 与预约。比较任务成功率、首音频时延、端点误判、打断恢复、数字准确度、语言混说、工具成功、人工评分和单分钟成本。没有结构化转写和工具调用审计的模型，不进入关键业务。

## 十一、现有功能不足

### 11.1 流程编排

**已有：** 画布、节点、边、模板、模拟运行、错误分支和多 Agent 入口。  
**不足：** 缺少真正的轮次事务、状态快照、节点级上下文隔离、确定性的边优先级、循环检测、发布迁移和生产回放。

改进重点：

- 节点只获取当前任务需要的 Prompt、变量、工具和知识；
- 边明确优先级，多个条件同时满足时结果可预测；
- 一次用户输入只消费一次，节点和边记录消费证据；
- 每轮有最大节点跳转数、重复状态检测和无进展检测；
- 生产通话可以按原始输入和版本回放，查看每个节点为什么进入/退出；
- 画布显示节点进入量、平均停留、退出和失败分布。ElevenLabs 已在工作流分析中把节点进入、时长、终止和边分布覆盖到图上。[25]

### 11.2 变量与实体

**已有：** 类型、默认值、来源、必填、使用范围、正则和“跨轮保留”。  
**不足：** 变量和实体还没有统一值模型，也没有生命周期、来源轮次、确认状态、版本、清除原因和冲突处理。

建议每个值至少包含：

```text
value, status(tentative/confirmed/rejected), scope,
source, source_turn_id, updated_at, expires_at,
confidence, consumed_by, version
```

建议作用域：

- `TURN`：只在当前客户话轮有效；
- `STEP`：离开当前步骤自动清除；
- `FLOW`：流程退出时清除；
- `CONVERSATION`：整通电话有效；
- `CONTACT`：客户长期资料，必须有写入权限和保存期。

实体是从输入识别出的候选值，变量是业务状态；实体通过验证/确认后再写变量，二者不能继续混用。

### 11.3 代码工具

**已有：** 流程代码节点支持 JavaScript/Python 和输入输出变量。  
**不足：** 代码附着在节点，难复用；没有依赖版本、密钥引用、网络白名单、CPU/内存/执行时间、输出 Schema、测试样例和发布版本。

建议升级为代码工具资源：浏览器式编辑、输入输出 Schema、只读密钥引用、允许访问域名、10 秒内短任务、无本地持久盘、日志脱敏、版本发布和回滚。流程仅引用已发布版本。超过限制的任务转异步工作流，不允许占用实时语音轮次。

### 11.4 记忆

**已有：** 记忆字段、是否进入 Prompt、脱敏、有效期和强制抽取。  
**不足：** 没有区分会话短期状态、客户事实、历史事件和操作规则；缺少写入确认、冲突、遗忘、来源证据和跨 Agent 权限。

LangGraph 公开模型将记忆分为会话短期记忆与跨会话长期记忆，长期又可分事实、经历和规则，并指出后台异步写入可以避免增加主链路时延。[26]

建议：

- 短期：对话摘要、当前目标、已确认实体，随会话结束归档；
- 客户事实：偏好、稳定资料，有来源、有效期、客户更正和隐私权限；
- 事件：过去通话、承诺和工具执行，只追加，不覆盖；
- 规则：仍由配置和版本管理，不让模型自行修改；
- 热路径只读取少量相关记忆，通话后异步抽取并去重；
- 敏感记忆默认不进入所有 Agent，按用途授权。

### 11.5 RAG

**已有：** 知识配置、向量/混合召回、Top-K、阈值和 RAG 工具。  
**不足：** 缺少数据摄取质量、文档结构切分、增量更新、权限、重排、引用、答案覆盖评测和问题诊断。

生产 RAG 建议补齐：

- 数据源连接、增量同步、失败重试、删除同步和版本；
- 按标题/段落/表格/FAQ 结构切分，不只按固定长度；
- 关键词 + 向量混合召回，再做语义重排；混合召回提高覆盖，重排提高精度，但需要控制额外时延。[27]
- 查询改写只用于检索，不替换客户原始问题；
- 每个片段保留来源、更新时间、产品、语言、租户和 ACL；权限必须在检索时过滤，不能召回后再靠模型隐藏。[28]
- 回答保留引用和使用的知识版本；低相关度时澄清或明确不知道；
- 用真实未命中问题建立离线集，评测 Recall@K、重排命中、引用正确和最终答案完整性。

### 11.6 打断速度

打断速度不是一个数，而是：

```text
用户开始说话 → VAD 检出 → 判断是真打断 → 停止服务端生成
→ 清空客户端音频缓冲 → 提交客户话语 → 开始新回复
```

当前已有灵敏度、强制打断词和忽略策略的配置基础，但仍缺：

- 服务器与客户端共同停止，避免服务端停了但缓存音频还在播放；
- 误打断识别与恢复；
- “嗯、好的”等附和语过滤；
- 电话回声、背景人声和当前客户声纹/声道区分；
- 被打断回答只保留客户实际听到的部分进入历史；
- 分阶段指标：VAD 检出、判定、停播、清缓冲各自耗时。

LiveKit 已把自适应打断、最短时长/词数、误打断恢复、预生成和噪声前处理放在统一话轮配置中；Gemini Live 也要求收到 `interrupted` 事件后立即清空客户端音频缓冲。[16][29]

## 十二、算法专题

### 12.1 提高意图识别准确度

不要只替换一个更大的模型。推荐四层路由：

1. 强规则：挂机、转人工、停止、号码确认等安全或高确定表达；
2. 候选召回：示例/向量召回 Top-K 意图；
3. 上下文判别：结合当前步骤、上一轮主题和已确认变量重排；
4. 拒识与澄清：最高分低，或 Top1/Top2 过近时不强行跳转。

Rasa 的公开 fallback 同时使用最低置信度和前两名差值处理低置信或歧义，这比单一阈值更稳健。[30]

必须按语言、渠道、机器人版本维护混淆矩阵，重点收集“跳错但没有报错”的隐性失败。意图标签要互斥、描述包含边界与反例；大而相近的意图优先用一个意图 + 实体/步骤区分。

### 12.2 话轮转换与小语种识别

小语种不能共用一个固定静音时长。语言的停顿、语速和填充词不同，电话窄带还会进一步影响 VAD/ASR。

建议：

- 先用声学 VAD 检出说话，再由多语语义话轮模型判断“意思是否说完”；
- 按语言/渠道设最小与最大等待，模型只在区间内动态决定；
- 不确定时采用短延迟，不抢答；达到最大等待则提交，避免无限静默；
- 保存“用户继续说导致上一轮取消”的比例，用真实数据校准；
- 小语种没有可靠语义端点模型时，退回 VAD + 较保守静音策略。

### 12.3 降噪与声纹

降噪、回声消除、旁人声音过滤和声纹身份认证是四件不同的事：

- 回声消除：去掉扬声器播放回灌；
- 噪声抑制：风声、键盘、道路等非语音；
- 主讲人隔离：保留当前客户，降低电视或旁人语音；
- 声纹验证：确认是否为登记人员，必须处理授权、活体和重放攻击。

优先顺序应是 AEC → 自动增益 → 电话/场景降噪 → VAD/ASR；声纹只用于明确需要身份保障的业务，不能把“声音像”当作唯一认证，也不能默认长期保存原始声纹。

### 12.4 打断识别与无关用户消息过滤

采用多信号融合，不让 LLM 独自决定是否打断：

- 音频信号：持续时长、能量、是否与 TTS 回声相似；
- ASR 信号：是否形成稳定词、是否只是附和词；
- 语义信号：停止/拒绝/纠正/新问题/旁人对话；
- 会话信号：当前播报是否可打断、是否处在支付/隐私告知等保护段。

输出三类：有效打断、附和不打断、疑似无关语音。疑似无关语音先不进入 LLM 主上下文，但短暂保留，后续若客户延续同一表达可合并恢复。误打断时恢复未播完内容或给自然衔接，不能从头重读。

### 12.5 ASR 多语种混合识别

需要区分“整段语言识别”和“同一句 code-switch”：

- 整段 LID 只选一个主语言，适合通话开始时选择模型；
- code-switch 模型能在同一音频流里识别多种语言，适合中文夹英文产品名等场景；
- 候选语言越多不一定越好。Google 明确建议只给最少候选语言，AWS 也警告候选不包含真实语言时会选一个最接近语言并产生错误转写。[31][32]
- Deepgram 的公开能力也区分主语言检测与实时多语言模型，实时混说应直接使用 multilingual 模型，而不是每句话反复切换单语模型。[33]

产品配置建议保留“主语言 + 最多 3 个候选语言”，后台根据厂商能力决定是多语言识别、自动 LID 还是多模型路由，并在 UI 标明实际能力。评测必须覆盖姓名、地址、数字、品牌和中英/本地语混说，不只看整句 WER。

## 十三、四个流程问题的完整修正方案

### 13.1 问题一：跳转不好用，客户继续使用大节点

根因不是画布不好看，而是拆节点后会产生上下文丢失、变量读取不确定、边判断不稳定和调试困难。

修正原则：

- 每个对话节点只完成一个目标，例如“确认身份”或“确认预约时间”；
- 当前节点 Prompt 是唯一活动任务，过去节点 Prompt 不继续进入模型；
- 过去结果只通过结构化状态和短摘要传入；
- 每个节点声明：需要输入、可写输出、允许工具、完成条件、失败出口；
- 边判断只读取节点允许暴露的已提交状态；
- 节点退出必须有明确原因：完成、用户换意图、失败、转人工或超时。

### 13.2 问题二：变量没有生命周期，导致边永远为 True

不能只给变量增加一个“清除”按钮。运行时要自动管理生命周期：

- 实体值先以 `tentative` 写入本轮候选区；
- 校验或客户确认后变为 `confirmed`；
- 边默认只能读取 confirmed 值，除非明确允许候选值；
- STEP/FLOW 变量在退出时自动清除；
- 条件边可配置“命中后消费”，同一个触发值不能无限重复命中；
- 每个用户话轮最多跳转 8 个节点（建议默认值），超过即进入循环保护；
- 保存 `(node_id, relevant_state_hash)`，同一轮再次出现相同状态即判定无进展循环；
- 循环后不继续猜，进入澄清、默认出口或人工处理。

### 13.3 问题三：End 后当前这句话不重新匹配

End 应表示“当前 Flow 完成”，不一定表示“当前客户话轮处理结束”。但也不能无条件把原句再跑一次，否则会重复执行。

建议引入“输入消费”模型：

- 每个客户最终转写生成唯一 `turn_id`；
- 意图、实体和文本片段记录是否已消费；
- Flow 完成后，如仍存在未消费的第二意图或客户在完成动作后又提出新要求，则用剩余意图重新匹配；
- 如果当前句只是完成当前 Flow 所需回答，则 End 后不再匹配；
- 一个 turn 最多重入一次全局路由，避免无限尾调用。

例如：“帮我查完账单后再办一个流量包。”查账单 Flow 完成后，第二个意图仍未消费，应进入办理流量包；“是的，就是这个号码”只用于完成身份确认，不应再次被当作新意图。

### 13.4 问题四：实体提取太晚，当前轮无法使用

推荐的单轮执行顺序：

```text
音频稳定终稿
  → 文本归一化与无关语音过滤
  → 全局意图候选 + 当前节点实体提取
  → 校验并提交本轮状态快照
  → 当前节点完成判断 / 边判断
  → 必要的工具或流程动作
  → 生成回复
  → 提交对话历史、消费记录和记忆写入任务
```

关键点：

- 本轮实体必须在当前节点 Prompt、工具参数和边判断前可见；
- 生成回复读取同一个不可变状态快照，避免执行中被别的异步任务改写；
- 工具成功后形成新的状态版本，再进行工具后分支；
- 记忆提取和通话质量评分放在回复后异步，不阻塞实时话轮；
- 同一变量多来源冲突时按“客户本轮明确纠正 > 工具权威结果 > 已确认历史 > 模型猜测”处理。

### 13.5 建议的运行时状态机

```text
LISTENING
  → TURN_FINALIZED
  → UNDERSTANDING
  → STATE_COMMITTED
  → ROUTING
  → ACTING（可选）
  → RESPONDING
  → TURN_COMMITTED
  → LISTENING

任一阶段失败 → FALLBACK / HUMAN_HANDOFF / END_SESSION
```

每次状态变化都记录会话 ID、turn ID、Agent、Flow、节点、配置版本和耗时。这样才能支持生产回放、PolyScore 类质量分析、流程节点漏斗和故障定位。

## 十六、最终判断

下一阶段不缺更多页面，而缺一个可靠的“语音 Agent 操作系统”：统一接收音频和文本，形成轮次，提取并管理状态，确定性地执行流程与工具，再用模型完成理解和表达。流程、变量、工具、记忆、RAG、多 Agent 和音频模型都应依附这条主链路，而不是分别建立自己的状态和执行规则。

先完成 P0 后，产品已有的画布、工具、记忆、监控和多 Agent 页面会真正变得可用；否则继续增加 MCP、Agent Loop 或端到端模型，只会让故障更难解释、配置更难迁移、客户更依赖“大节点大 Prompt”。
