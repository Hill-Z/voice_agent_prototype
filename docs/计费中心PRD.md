>   1. **余额改批次制**：钱不是一个池子，是一笔一笔的额度批次，各有有效期。资金分三种性质：`voucher`（随套餐给的映射额度，有有效期）、`cash`（客户单独充值，无限期）、`credit`（平台授信，自有资金用尽后兜底）。充值方式分两类：系统自动充值（走代金券体系、有有效期）/ 单独充值（无限期）。

>   3. **折算分钟数从面客的余额与汇总页下线**：单价是动态的，今天折出 28 万分钟、明天调价变 19 万，客户会拿第一次看到的数去对。余额、已用、汇总一律只给金额口径。（唯一保留折算的地方是机器人编辑页的单价条——那个分钟数就写在单价旁边，答案与依据同一行。）

## 1. Problem Statement

客户把语音机器人买回去之后，**只能看到「买了什么」，看不到「钱花到哪儿了」**：控制台里能查机器人、能查通话记录、能查报表，但没有任何一个页面回答「账户还剩多少钱、这笔钱什么时候到期、能欠多少、每个机器人花了我多少钱」。当客户发现模型配置从便宜档换成贵档、或者某个机器人明显更费钱时，拿不到可核对的凭据。

同时，**平台侧也没有把定价变成可执行的产品能力**：单价现在只存在于商务报价里，客户每改一次 ASR / 大模型 / TTS 配置，成本就变了，但没有任何地方算出「这个机器人现在每分钟多少钱」，也没有在发布时把当时的配置快照和费率留痕。结果是每一通电话事后都说不清为什么是那个价格，对账只能人工拉数据。

不解决的代价：**（1）账单争议和人工对账成本持续存在；（2）客户为了省钱不敢换更好的模型，高配模型卖不动，ARPU 上不去；（3）「按用量计费」这个商业模式在控制台里没有落地，客户无法自助。** 证据：本仓库现有 30+ 个业务模块中，与计费相关的只有业务侧的价格表工具（`components/tools/PricingConfigurationWorkspace.tsx`，给机器人做业务报价用）和实时监控里的「并发使用率」指标（`components/report/realtimeMonitoringData.ts`）——**平台自身的计费能力缺口为 0 覆盖率**。

## 2. Goals

| # | 目标 | 怎么知道成了 |
|---|---|---|
| G1 | **客户能自助回答「我还有多少钱、还能欠多少、这笔钱什么时候到期」**，不用问客服 | 计费中心打开后首屏（不需任何点击）同时可见「账面余额」与「可用额度」（含可用授信）；演示中该页面在无人讲解下能被非技术同事指认出这两个数字，并说出「余额用完了会怎样」 |
| G2 | **每一通电话的费用可追溯到具体配置**，并给出人话解释 | 任意一条通话消费明细都能展开到「用了哪个 ASR / 哪个大模型 / 哪个 TTS → 档位 → 费率 → 本通费用」，不出现只有一个总价的黑盒 |
| G3 | **发布机器人时单价当场可知**，配置变了价格当场变 | 发布弹窗内显示该机器人的适用费率；在基础配置里改大模型档位后，费率预览在 1 次渲染内更新，无需保存 |
| G4 | **按机器人下钻的月度消费可查**，支持从月份一路点到单通电话 | 从「消费统计」的某机器人某月，能展开到按天，再从某天跳到「通话消费明细」并带上筛选条件，全程不超过 3 次点击 |
| G5 | **定价逻辑是可信代码，不是散落的硬编码** | 存在一个纯函数把「机器人配置 + 成本参数表」映射成费率；覆盖最低价兜底、取整边界、未知模型三类边界；仓库静态检查脚本通过 |

业务目标（平台侧）：让「换更好的模型 → 单价更高 → 收入更高」这条路在控制台里可见、可解释，从而敢卖高配档。

## 3. Non-Goals

明确不做，逐条给理由。

1. **不做真实充值、购买、续费、退款。** 原型是纯前端，没有任何后端和支付通道；页面上任何「付款」都只能是不可点击的占位或说明。做半个支付流程比不做更危险。
2. **不做发票开具、账单 PDF 下载、对公转账、开票信息管理。** 属于财务系统职责，需要税务和财务流程对接，与本模块的「用量与消费记录」不是同一件事。
3. **不做优惠券、折扣、阶梯量价、包年包月自动续费、协议价。** 这些会让定价公式从「成本 ×2 + 最低价」变成一张二维的价格策略表，是独立的价格管理模块，会直接把本期拖垮。
4. **不做多租户 / 代理商 / 子账号分账。** 原型仓库是单租户演示（`App.tsx` 里 `bots` 是全局数组，没有租户维度）。引入租户维度是架构级改动，不属于计费中心。
5. **不做余额耗尽后的停机、降级、自动转人工策略。** 这会改机器人接通行为，属于对话运行时，需要和「转人工」「挂断策略」一起评审。本期只做「余额不足的提示」，不做「余额不足的处置」。
6. **不做内部成本-收入对比的毛利看板。** 成本参数是定价的输入，会在单价明细里以「内部视角」出现，但不做按机器人/按时段的毛利报表。
7. **不做账单争议与申诉流程。** 需要工单系统和客服流程。
8. **不改动 `components/tools/PricingConfigurationWorkspace.tsx` 及其价格表能力。** 那是**给机器人做业务报价用的工具**（家政/商品价格表），与**平台向客户收费**完全无关。名称相近，实现时必须避免复用、避免互相 import，避免在文档和代码里用同一个「计费」二字指代两件事。本 PRD 中「计费」一律指平台向客户收费。
9. **不做按 token / 按字符直接向客户计费。** 客户侧只有一个口径：**按通话时长计费**。成本侧的分项（ASR 小时、TTS 字符、LLM token）只用于反推费率，不对外暴露为计费项。

## 4. 用户与角色

| 角色 | 关心什么 | 在计费中心里的主要动作 |
|---|---|---|
| **客户方决策人**（买套餐的人） | 还剩多少钱、能欠多少、要不要加购 | 看余额、可用额度与到期日 |

## 5. User Stories

按优先级从高到低。P0 的故事必须全部落地，功能才算可用。

**客户方决策人**
1. 作为客户方决策人，我想在打开计费中心的第一屏就看到账户还剩多少钱、还能欠多少、这笔钱什么时候到期，这样我不用问客服就知道要不要充值。
2. 作为客户方决策人，我想看到我买了几路并发、现在用了多少，这样我能判断要不要加购并发。
3. 作为客户方决策人，我想在余额快用完、已经用尽、已经欠费这三种时候收到邮箱和短信提醒，而且事后查得到提醒发过没有，这样我不会等到机器人打不出电话才发现，也不至于跟平台就「到底提没提醒」扯不清。

**客户方运营 / 对账人**

4. 作为对账人，我想按时间范围、机器人、通话类型筛选出一批通话，看到每一通的时长、单价和扣费金额，这样我能和我的业务台账对上。
5. 作为对账人，我想点开某一通电话看到「它用了哪个语音识别、哪个大模型、哪个音色，所以单价是这个数」，这样客户来问的时候我答得上来。
6. 作为对账人，我想选一个月份、按机器人看这个月每个机器人花了多少钱、打了多长时间，这样我能判断哪个业务线在烧钱。
7. 作为对账人，我想从某个机器人的某个月展开到按天的明细，再从某天直接跳到那天的通话明细，这样我不用在两个页面之间来回抄筛选条件。
8. 作为对账人，我想把这段时间的充值记录、扣费记录、通话消费明细、消费统计和提醒记录分别导成文件，而且每一列是什么、怎么算出来的写在页面上，这样我能自己核一遍账，也能交给财务存档。

**客户方机器人配置人员**

9. 作为配置人员，我想在改完 ASR / 大模型 / TTS 之后马上看到这个机器人的每分钟单价，这样我在保存前就知道成本变化。
10. 作为配置人员，我想在点「发布」的确认弹窗里再看到一次这个单价，这样我不会误发布一个我没意识到变贵了的配置。

**平台运营（内部）**

11. 作为平台运营，我想在费率明细里核对这台机器人的成本构成和加价后的报价，这样我能确认定价公式没算错。

**边界与异常故事**

12. 作为对账人，当某通电话用的模型组合还没有配价格时，我想看到明确的「待定价」状态和一句能转述给平台运营的话，而不是看到一个 ¥0.00 —— 因为 ¥0.00 会让我以为这通电话免费。
13. 作为对账人，当某个机器人已经被删掉时，我想在历史消费里仍然看到它、并被告知它已删除，而不是这个月的数字莫名其妙变小。
14. 作为客户方决策人，当这段时间确实没有通话时，我想看到「这段时间没有通话，所以没有消费」而不是一张空白表格。
15. 作为对账人，当账户从没触发过提醒时，我想看到「还没有发出过提醒」并说明什么情况下才会有一条，而不是看到几行编出来的记录——编出来的记录会让我以为真的收到过提醒。

## 6. 关键决策

这一节是本 PRD 与「把口述抄成需求」的区别所在。三件事必须先定，否则实现会分叉。

### 6.1 定价模型与口径

**费率公式**（对外报价，单位：元/分钟）：

```
成本合计（微元/分钟，整数） = ASR成本 + TTS成本 + LLM成本
报价列表                    = 成本合计 × 2                             （markupRatio = 2）
取整后                      = 向上取整到 0.01 元（10 厘）的报价列表        （priceGridMilli = 10）
适用费率                    = max( 底价 0.15 元/分钟（150 厘）, 取整后 )   （priceFloorMilli = 150）
```

定价规则版本号 `v1-A`。触底标记 `floorApplied` **只在「取整后严格低于底价」时置位**；取整后正好等于 0.15 不算触底（结果相同，不需要显示「已按最低价计费」）。

**单位刻度（写死，不要出现二进制浮点）**：1 元 = 100 分 = 1000 厘 = 1,000,000 微元。**成本用微元、单价用厘、金额用分**，全链路整数运算。

**成本分项参数**（均为「每分钟通话」口径）：

| 分项 | 计费单位（供应商侧） | 折算成每分钟通话 |
|---|---|---|
| ASR | 元 / 小时 | `单位价 × (每分钟有效语音秒数 ÷ 3600)`，中文默认**每分钟 50 秒**有效语音（`asrSpeechSecPerMin: 50`） |
| TTS | 元 / 万字符 | `单位价 × (每分钟字数 ÷ 10000)`；每分钟字数 = 每分钟播报秒数 × 每秒字数 = 30 秒 × 4 字 = **120 字/分钟**（中文，`ttsSpeakSecPerMin: 30` × `ttsCharsPerSec: 4`），按语言分别配置 |
| LLM | 元 / 百万 token（输入） | `单位价 × (每分钟输入 token ÷ 1000000)`，默认 10000 token/分钟。**输出 token 单价暂缺**（`outputPriceMissing: true`、`outputTokensPerMin: 0`），当前只计输入 token 成本，快照里显式标记这个已知的保守偏差 |

**计费时长口径（本 PRD 的关键定义，必须写死在文案和代码里）：**

- 计费时长 = **AI 接听到通话结束的时长**（秒），即 `CallRecord.duration` 的同一口径。
- **不计费的部分**：振铃等待、未接通（`status` 为 `no_answer` / `busy` / `failed`）、通话建立前的排队。
- **含在计费时长内的部分**：静音、机器人等待客户回应、客户沉默。理由：成本参数里的「每分钟 50 秒有效语音」已经把这个差额吸收进成本估算，两者口径自洽；而且「按通话时长」是客户能在通话记录里自己核对的口径，「按有效语音时长」客户无法验证，是争议源头。
- 金额按秒计算，**向上取整到分**：`金额（分）= 向上取整( 计费秒数 × 单价厘 ÷ 600 )`，不按「不足一分钟算一分钟」进位。是**向上取整，不是四舍五入**（`ceilDiv`），即宁可多收不足一分钱，也不把成本抹掉。
- 计费时长为 0 秒（例如未接通）时金额为 0，不产生任何扣费。

> 一段通话如果中途转人工，转人工之后的时长是否计费，本 PRD 不擅自决定 —— 见 Open Questions Q6。P0 的实现按「AI 通话部分计费，转人工后的时长单独列一列但计入 0 费用」处理，并在页面上用一句话说明。

### 6.2 成本模型 ↔ 现有模型枚举的缺口（关键决策）

**已核实的现状**：用户给的内部成本表用的是**千问 ASR、千问 plus / 千问 max、MiniMax TTS**。但仓库 `types.ts` 的三个枚举里**没有这些值**：

- `ASRModel`（`types.ts:28`）：Whisper V3、Azure STT、AWS Transcribe、Google STT、Volcengine ASR、腾讯系 12 个 —— **无千问 ASR**
- `TTSModel`（`types.ts:20`）：自研 TTS、Gemini TTS、Azure TTS、OpenAI TTS、Volcengine TTS —— **无 MiniMax**
- `ModelType`（`types.ts:3`）：Gemini Flash 2.0、Gemini Pro 1.5、GPT-4o、Claude 3.5 Sonnet —— **无千问 plus / 千问 max**

**决策：P0 采用「内部成本模型表」（方案 B），不用「扩充枚举」（方案 A）。**

| 方案 | 内容 | 评价 |
|---|---|---|
| A. 扩充枚举 | 往 `ASRModel` / `TTSModel` / `ModelType` 里加千问、MiniMax 的枚举值 | 会让这些模型出现在机器人配置的下拉里 —— 但**平台此刻根本没有接入这些模型**，选了就选了一个跑不通的模型。而且 `BotBasicConfig.tsx` 里 ASR 是「厂商 → 模型」二级联动（`ASR_PROVIDER_OPTIONS`，含语言与 languageCodes），TTS 下拉还有「仅自研 TTS 支持数字慢读」这类基于枚举值的分支（`supportsIdentifierSlowReading`，`BotBasicConfig.tsx:120`）。加枚举会牵动 4 处联动与分支，属于中风险改动 |
| **B. 内部成本模型映射表（采纳）** | 在计费中心内部维护一张独立的 `BillingCostModel[]` 表，作为**成本口径的唯一事实来源**；表里每一项通过 `boundModelValue?` 声明它对应现有枚举里的哪个值，`boundModelValue` 为空表示「已定价但当前机器人配置里还选不到」 | 计费逻辑与机器人配置表单解耦：供应商调价只改这张表，不动配置表单；现有枚举一个都不改，存量机器人配置零影响；千问/MiniMax 的定价参数可以现在就录进去，等真正接入模型时只需把 `boundModelValue` 填上，计费侧零改动 |

**为什么倾向 B（三个理由，按权重排序）**：

1. **风险最低**。现有 `ASRModel` 有 16 个值、`TTSModel` 5 个值，且被机器人配置表单、调试、评测、通话记录多处消费。改枚举的收益只是「客户能选到千问」，而代价是可能改坏正在演示的模型选择交互 —— 这笔交易在原型阶段不划算。
2. **职责边界正确**。用户明确说「**计费中心自己负责计算**」。成本参数是计费中心的数据，它不该寄生在机器人配置的枚举上。供应商价格和「客户能选什么模型」是两件变化节奏完全不同的事。
3. **为 P1 留了路**。等真要接入千问 ASR / MiniMax 时，那是一次独立的模型接入需求（要改 `ASR_PROVIDER_OPTIONS`、语言映射、可能的联调），和本次计费模块解耦交付。B 方案下，模型接入那天只需要把 `boundModelValue` 从 `undefined` 改成 `ASRModel.QWEN_ASR`，计费逻辑一行不动。

**映射表结构（P0 必须落地）**：

```ts
export interface BillingCostModel {
  id: string;                    // 'asr.qwen.general' / 'llm.qwen.max' / 'tts.minimax.std'
  category: 'ASR' | 'TTS' | 'LLM';
  displayName: string;           // 「千问 ASR」——用于「内部视角」展示
  boundModelValue?: string;      // 对应 ASRModel/TTSModel/ModelType 的值；undefined = 已定价但暂不可选
  unit: 'per_hour' | 'per_10k_chars' | 'per_million_tokens';
  unitPrice: number;             // 元
  effectiveFrom: string;         // 生效日期，为将来调价留痕
  estimated?: boolean;           // true = 演示估值，供应商真实采购价待补
}
```

**查表口径**：先按 `category + boundModelValue` 找绑定项，找不到再按 `id` 找。按 `id` 兜底是为了让「配置里还选不到、但已经有定价」的模型（如千问、MiniMax）也能用在演示数据和历史机器人上，不必为了计费去扩配置枚举。表版本号 `COST_TABLE_VERSION = 'cost-2026-01'`（生效日 `2026-01-01`）。

**必须有的兜底（这是本条决策里最容易漏、后果最严重的一条）**：

计费引擎查不到某台机器人当前配置对应的成本模型时，**不允许返回 0，也不允许静默套一个默认值**。必须返回一个显式的「待定价」结果，由 UI 呈现为「待定价」，且**该笔费用不计入任何合计**（见 §7.12 异常态 A1）。

### 6.3 客户端可见性：成本能不能给客户看

用户的口述里同时出现了「成本」和「对外价 = 成本 × 2」。这两件事**不能同时出现在客户看的页面上** —— 把成本列给客户，等于把 2 倍加价率直接摊开给客户看。

**本 PRD 的处理（待用户拍板，见 Q3）：**

- **默认视图（客户视角）**：只展示三样东西 —— ① 用到的模型组合（如「大模型：千问 max / 语音识别：腾讯中文大模型 / 音色：MiniMax」），② 一个**档位名**（如「标准档 / 高配档」），③ **最终适用费率**。
- **内部视角**：在计费依据面板右上角提供一个默认关闭的「内部视角」开关；打开后追加展示三行成本分项、成本合计、×2 后的报价、取整过程、最低价兜底说明。这个开关在当前原型里是**演示开关**，真实产品里应由权限控制。
- **理由**：客户要的是「为什么是这个价」的**可解释性**，不是平台的成本结构。「用了千问 max 所以贵」已经足以解释，且不会泄露加价率。同时内部视角保留给平台运营核对公式，也方便本原型在演示时讲清整套定价逻辑。

## 7. 信息架构：计费中心页面结构

> 这一节细到可以照着搭。所有文案都是最终要落在页面上的中文，不含「锁定」这类内部术语。

### 7.1 导航与路由

- **侧边栏**（`components/ui/LayoutComponents.tsx` 的 `menuItems`）：新增一个**一级菜单项**，`icon: Wallet`（lucide-react），`label: '计费中心'`，`id: '计费中心'`，**不带子菜单**。位置放在「监控报表」分组之后、「短信管理」之前。
  - 理由：计费中心是运营/财务的阅读动线，和「综合报表」「实时监控」属于同一类「看数据」的场景；放进「基础设施」分组（集成中心/通信网关/系统设置）会让人以为它是配置项。
- **路由**（`App.tsx` 的 `renderContent()`）：新增 `case '计费中心': return <BillingCenter bots={bots} />;`
  - 计费中心需要机器人列表来推导费率（它是唯一持有 `bots` 的组件），所以从 `App.tsx` 通过 props 传入，和 `SatisfactionSurveyManager`、`SeatManager`、`OutboundTemplates` 的既有做法一致。
  - `Header` 的标题沿用 `activeMenu`，即显示「计费中心」，无需改动。

**实现落法（与设计稿不同）**：没有插进「监控报表」分组，而是**新开了一个分组「账户与计费」**（`{ type: 'header', label: '账户与计费' }`）放在侧边栏末尾。理由：放进「监控报表」分组的话，这一项和「综合报表 / 实时监控 / 短信管理」并列，客户会以为它也是报表的一种；而计费的读者是拿它对账的人，和看运营报表的人不是同一批，权限将来也不会一样（见 Q15）。**新开一个分组也让后续「充值 / 发票 / 套餐管理」有地方放**，不必再动报表分组。

**路由实现（与设计稿不同）**：`case '计费中心': return <BillingCenter />;` —— **没有传 `bots`**。计费侧的机器人档案（`BILLING_ROBOT_PROFILES`）自带费率和状态，而 `bots` 是页面里的演示机器人配置，两者是不同的数据集：接进去只会让「计费中心里的机器人」和「机器人列表里的机器人」变成两处定义、慢慢分叉。费率由 `billingData.ts` 从档案里推导，不依赖 `bots`。

### 7.2 常驻区块：账户概览条

位于页面顶部、**不随页签切换**（因为「我还有多少钱」是任何一个页签下都想看到的信息）。

四个指标卡（复用 `components/report/reportUi.tsx` 的 `StatCard`，保持与监控报表一致的视觉）。**卡片集已于 2026-09-23 重做**，下面这张表是当前口径：

| 卡片 | 主数值 | 副标题（小字） |
|---|---|---|
| 余额（截至今日） | `¥42,689.74` | 代金券额度 ¥42,689.74（2027-03-01 到期）· 单独充值 ¥0.00（无限期） |
| 可用额度（截至今日） | `¥52,689.74` | 已含可用信用额度 ¥10,000.00 · 通话中预占 ¥0.00 |
| 本期消费（本月） | `¥195.77` | 通话 812 通（其中智呼 N 通）· 时长 810 分钟 |
| 本期充值（本月） | `¥0.00` | 这段时间没有充值到账 |

> 表内数字是当前实现里的演示数据，只作形状示例；口径以文字为准。
>
> **三处已作废的旧卡**（2026-09-23 修订）：
> - **「话费余额」** → 改「余额」。余额是语音智能体的余额，不是话费；话费是运营商的概念，客户会以为要充到手机号里。
> - **「剩余可用时长（约 34,598 分钟，按最低档折算）」** → **整张卡删除**。单价是动态的，今天折出 28 万分钟、明天调价变 19 万，客户会拿第一次看到的数去对账，而对不上。
> - **「累计通话」** → 并入「本期消费」的副标题。「多少通通话、多少智呼的时长」是客户点名要的两个数，只给累计通数等于没回答。
>
> **余额与可用额度两张卡都不跟时间范围筛选走**，标题上标「截至今日」：筛选变的是「这段时间花了多少」，不是「现在还剩多少」。不标的话，客户切到上个月会以为看到的是上个月的余额。
> **余额看的是自有资金**（代金券 + 单独充值），不含授信——把授信算进来，余额早就见底了这条提示却一直不出现，而那正是客户最需要被提醒的时候。
> 「折算可用时长」的口径说明不进脚注——这张卡已经删了，折算值在面客的余额与汇总口径里一律不再出现。

**余额不足提示条**（仅当**账面余额**低于**映射额度总额的 20%** 时出现）：位于概览条正下方，浅琥珀色背景 + 一行文案，**不使用弹窗、不使用红色**。文案按有无可用授信分叉：

> 余额已经不到映射额度总额的 20%，建议及时充值。余额扣完后会先动用信用额度垫付（当前可用 ¥10,000.00），垫付的部分形成欠费，欠费未结清时新的通话将无法发起；正在通话中的不会中断，会按实际时长扣到本通结束；充值到账后即可继续发起通话。

> 没有可用授信时，中间那句换成「余额扣完后新的通话将无法发起；」。**有授信却不说**，客户会以为钱花完了电话立刻停；**没授信却说了**，客户会以为还有一笔钱可以花。两种说法都不行，所以文案必须按实际情况分叉。
> 演示数据里余额还剩约九成，所以原型上看不到这条提示——这是对的，余额够的时候不该吓客户。要演示这条路径，把阈值常量调到 0.95 以上。
> **这句话回答的是「钱花完了会怎样」，不是「并发被占满怎么办」**（原稿写的是后者）：客户按「排队等一路空出来」去理解，会得出「充钱能解决排队」的错误结论——余额和并发是两件事。

**待定价提示条**（与上条同区、可同时出现）：当有机器人算不出单价时，列出是哪几台、缺哪一项配置，并说明这些机器人上的通话不扣费。文案见 §7.12 异常态 A1。

> 「今天」取**数据截止日**而不是 `new Date()`：原型没有实时钟，用真实当天的话，换一天打开「本月」会变成一个演示数据里没有的月份。

### 7.4 页签 1：余额与额度（原「用量与余额」）

**改名理由**：这一页回答的是「还剩多少、哪笔什么时候到期」，不再回答「花了多少」——后者在资金流水与消费统计里。名字和它回答的问题是同一件事，客户才不会点错页签。

内部**七个区块，按此顺序**（与新账户建账的顺序一致：先看余额由哪几笔组成，再看能欠多少，再看每一笔的到期日，再看买过什么套餐，再看提醒设置，再看并发，最后看定价口径）：

#### 区块 1.1 余额构成

**五行分项 + 两行合计**，回答的是「我这笔钱是什么性质、会不会过期」：

| 行 | 值 | 说明 |
|---|---|---|
| 代金券额度 | `¥42,689.74` | 随套餐一起给的额度，有有效期，到期没用完会清零 |
| 单独充值 | `¥0.00` | 你自己充值进来的钱，没有有效期，不会清零 |
| 冻结中 | `¥0.00` | 通话进行中先占住的那部分，打完按实际费用结算，多占的马上退回 |
| 信用额度 | `¥10,000.00` | 能欠多少（**不是账上的钱**，见区块 1.2） |
| 欠费 | `¥0.00` | 动用授信垫付的那部分，需要结清 |
| **账面余额** | `¥42,689.74` | = 代金券额度 + 单独充值。**不含授信** |
| **可用额度** | `¥52,689.74` | = 账面余额 + 可用授信 − 冻结中。**这才是现在真能花的钱** |

> **账面余额与可用额度必须同时给**，并写明前者不含授信：只给一个数，客户要么以为账上凭空多了一笔自己没充过的钱（把授信算进余额），要么以为授信不能用（只给余额）。
> 代金券额度那一行要标出**最近的到期日**（取所有代金券批次里最快到期的那个）；没有代金券或已用光时留空，**不编一个日期出来**。

#### 区块 1.2 信用额度

一句话说明：**「余额不够时，平台先替你垫上多少。」**

四张小卡（`lg:grid-cols-4`）：

| 卡片 | 值 | 说明 |
|---|---|---|
| 授信额度 | `¥10,000.00` | 平台核定，客户不可自行调整 |
| 已用（欠费） | `¥0.00` | 已经垫付出去、还没结清的部分；大于 0 时红色 |
| 可用授信 | `¥10,000.00` | 还能透支多少 |
| 有效期至 | `2027-03-01` | 到期后未用部分失效，已欠的仍要结清 |

下方一行「开通时间」+ 四条口径：

- **扣费顺序：先扣快到期的代金券额度，再扣单独充值的钱，最后才动用授信。** 动用授信就是欠费，需要结清。
- **欠费不会自动从余额里补扣**，要在账户里结清；**欠费未结清期间无法开通新的通话**，正在通话中的不会中断。
- 授信额度由平台核定，客户不能自行调整；需要提高额度请联系客户经理。
- 余额低于预警值、余额用尽、已经欠费这三件事都会发提醒，提醒记录在「通知记录」页逐条可查（见 §7.8）。

**未开通授信的账户整块换成一句话**（「当前账号未开通信用额度。需要开通或调整额度，请联系你的客户经理。」），**不给一个四张零的卡片组**——四个零看起来像「开通了但没钱」，客户会来问为什么。

> **授信不是钱包**：开通授信不产生到账流水、不让账面余额变多，只体现在「可用额度」里。把能借的钱算成已有的钱，客户会以为账上凭空多了一笔（见 §7.2）。

#### 区块 1.3 额度批次明细（原「余额明细」）

一句话说明：**「每一笔到账的钱分别还剩多少、什么时候到期。」**

| 列 | 内容 |
|---|---|
| 来源 | 如「标准套餐 A（1 万元）· 系统自动充值」 |
| 到账时间 | `2026-03-01 10:12` |
| 原始金额 | `¥7,500.00` |
| 剩余金额 | `¥5,189.74`（加粗） |
| 有效期至 | `2027-03-01` 或「无限期」 |
| 状态 | 生效中 / 已用完 / 已过期 |

**到期提示条**（表格上方，只在真有批次要到期时出现）：**「{批次名} 将在 N 天后（{到期日}）到期，剩余 ¥X。到期没用完的部分会清零，不会结转到下一期。」** 剩余天数进入预警区间时用琥珀色。**没有批次要到期时这一条自然消失**，不留一个空提示。

扣费时**按到期日从近到远扣**（先扣快到期的），所以不会出现「现金余额还在、代金券却过期了」。

**到期清零的时点**：按批次到期日的 `00:00` 清零（2026-03-01 生效、有效期一年 → 2027-03-01 00:00 清零）。清零会**留一条流水**（`expire` 类型），余额链不断——不留的话客户会看到余额莫名少了一块，而对不上任何一笔。

**这里的「有效期至」与账户整体不是一回事**：账户没有「总到期日」，每笔批次各算各的；客户问「我的钱什么时候过期」，回答的永远是「最近这一批什么时候过期」。

批次通常个位数，不加筛选器；超过 5 条时补一个状态筛选。

#### 区块 1.4 套餐

一句话说明：**「你买过的套餐。套餐金额和你账户里能打电话的余额不是同一个数。」**

| 列 | 内容 |
|---|---|
| 套餐 | 如「标准套餐 A」 |
| 购买时间 | `2026-03-01 10:12` |
| 并发 | `1 路` |
| 套餐金额 | `¥10,000.00` |
| 其中映射额度 | `¥7,500.00`（加粗） |
| 其中平台与并发服务费 | `¥2,500.00` |
| 有效期至 | `2027-03-01` |

> **这一块是「7500 不是话费」这条口径唯一说全的地方**：1 路并发的套餐 ¥10,000 里，¥7,500 是**映射到余额上的额度**（能打电话、有有效期、到期清零），剩下 ¥2,500 是平台与并发服务费（不进余额、不能打电话、不随余额清零）。
> **6 路并发 = 套餐总额 ¥60,000**，映射额度 6 × ¥7,500 = **¥45,000**——不是「6 路各扣一次 1 万之后还剩 1.5 万」。
> 「映射额度」这个说法的理由：客户说「7500 元」，指的是一整套东西里映射到余额上的那部分钱。叫「话费」会让人以为要充到手机号里（见 §7.2）。

#### 区块 1.5 预警设置

一句话说明：**「余额快用完时提醒你，避免通话因为余额耗尽而发不出去。」**

| 列 | 内容 |
|---|---|
| 提醒档位 | 三档：余额低于预警值 / 余额已用尽 / 已经欠费 |
| 什么时候提醒 | 第一档写「账面余额低于你设的 ¥5,000.00 时提醒」；后两档写各自的触发条件 |
| 能不能关 | 第一档「可调整预警值」；后两档「必提醒，不能关闭」 |

四个可改项排一行（`lg:grid-cols-12`）：**预警值**（元，数字输入）/ **提醒方式**（邮箱、短信两个勾选，至少选一种）/ **邮箱接收人** / **短信接收人**，外加一行「保存设置」按钮与保存后的回执句。

> **一种方式都不选等于「不提醒」，而这个功能存在的意义就是提醒**：所以勾掉最后一个渠道时按钮直接禁用并给一句「至少要选一种提醒方式，否则余额用尽时你不会收到任何提醒」，而不是保存之后再报错。
> **频率上限不给改**（同一档每天最多 1 次、最多连发 3 天）：这是防打扰的下限，不是客户偏好。
> **页面顶部那条余额不足提示条用的是另一个阈值**：提示条固定按「账面余额低于映射额度总额的 20%」触发（见 §7.2），而这一页的预警值是客户自己设的一个数（演示账户是平台默认的 ¥5,000）。两者可以不一致——客户看到的是「页面上的统一提示」和「我自己定的线」两种东西，不必也不该合成一个。

#### 区块 1.6 并发容量

一句话说明：**「你买了几路并发，分配给了谁、还剩几路可分配。」**（表格副标题里把「买了 6 路、分配给 5 台在用机器人 5 路」写全。）

筛选器：时间范围（今日 / 昨日 / 最近 7 天）。切换后**表头文案与数据一起变**（「今日峰值并发」→「昨日峰值并发」），汇总行同步变化——不允许出现点了没反应的开关。

| 列 | 说明 |
|---|---|
| 机器人 | 机器人名称；只看还在用的（已删除机器人不再占并发） |
| 已分配并发 | `3 路` |
| 今日峰值并发 | `2 路`（表头随范围变化） |
| 通话前预占额度 | `¥5.85`；该机器人各路的预占额度之和；**算不出单价的机器人显示「—」**，`title` 说明「这台机器人的模型还没有配置价格，算不出要预占多少」 |
| 今日被限流次数 | `0 次`；大于 0 时该单元格用琥珀色文字（表头随范围变化） |

表尾给出三列合计，以及「已购 6 路 / 已分配 5 路」的对照——**只说已分配 5 路，客户不知道自己买了 6 路。**

**并发预占口径（必须写进表格下方的小字，且用客户看得懂的说法）**：每路并发在通话开始前先按**最长 5 分钟**预占一笔额度，`单路预占（分）= 向上取整( 5 × 单价厘 ÷ 10 )`；电话打完立刻按实际产生的费用结算，**多占的部分马上退回，不需要客户操作**。余额不足以覆盖一次预占时，新的通话会先排队等一路空出来（这就是「被限流次数」），而不是让某一路打到欠费；已经在通话中的不会中断。

> 术语约束：不出现「冻结」「估价」这类词，统一叫「预占额度」——客户听不懂金融术语，但听得懂「先占住、打完退回来」。
> 这与「余额用尽」是两件事：余额和并发都会让新通话打不出去，但原因和解决办法都不一样，文案里不能混（见 §7.2）。

空状态文案（该账户下没有已发布的机器人）：**「还没有已发布的机器人，发布后这里会显示并发使用情况。」**

#### 区块 1.7 费用怎么算（原「费率说明」）

静态说明块，**不含任何可点击元素**。文案：

> **费用怎么算**
> 你的费用按每通电话的**通话时长**计算，按秒计费、金额**向上取整到分**，不会把不足一分钟的通话按整分钟收。
> 每一通接通的电话**最低收 0.01 元**；未接通的电话不计费。
> 振铃等待时间不计费；通话中的静音与等待客户回应的时间照常计费。
> 每分钟单价由这个机器人使用的**语音识别、大模型和音色**共同决定：模型越强，单价越高。当前平台最低 0.15 元/分钟。
> 更换模型会重新算价，但已经打完的电话仍按当时的单价计费，不会追溯调整。
> 每个机器人有各自的单价，所以同一笔余额在不同机器人上能打的时长不一样。
> **扣费顺序：先扣快到期的额度，再扣没有有效期的余额，最后才动用信用额度。信用额度一旦动用就是欠款。**

> 「不足 1 分按 1 分收」与「不会按整分钟收」必须分成两句：都写成「不足 1 分按 1 分算」的话，上一句刚说完「不会按整分钟收」，下一句看起来就是在按整分钟收——一句说金额、一句说时长，客户才不会读岔。

### 7.5 页签 2：资金流水

一句话说明（页面副标题）：**「每一笔钱什么时候进来的、什么时候被扣掉的。」**

**充值记录与扣费记录是同一本账的两种视角，所以用子页签切，不另开两个页面**——分成两个页面之后，客户想看「这个月一共进来多少、出去多少」就得自己把两边加起来。

三个子页签（分段按钮，不是下拉：只有三项且互相排斥，摊开比收进下拉少一次点击，也能一眼看出「还有充值记录这类东西」）：

| 子页签 | 表里是什么 | 列 |
|---|---|---|
| 全部 | 这段时间里所有动过余额的流水，含通话前预占与预占释放 | 时间 / 流水号 / 类型 / 说明 / 金额 / 期初余额 / 期末余额 |
| 充值记录 | 钱进来的记录 | 时间 / 流水号 / 充值方式 / 到账金额 / 资金形式 / 有效期至 / 期末余额 / 状态 |
| 扣费记录 | 每一通电话实际扣掉的钱，以及从哪一笔额度里扣的 | 时间 / 流水号 / 机器人 / 计费时长 / 单价 / 扣费金额 / 扣减来源 / 期初余额 / 期末余额 |

> 「全部」不是第三个筛选条件，是「不做筛选」。**扣费记录只列真正扣钱的那一类**（`call_charge`），预占与释放归在「全部」里——它们也动余额，但一笔一进一出，放进扣费记录会让客户以为每通电话被扣了两次。
> 「资金形式」指这笔钱的性质：系统自动充值进来的是代金券额度（有有效期、到期没用完会清零），单独充值的钱没有有效期。**「无限期」必须写出来**，留空客户会以为漏了。

**表尾一行**：本范围共 N 笔 ｜ 进账 / 支出（或「到账合计」「扣费合计」）｜ 期末余额。**期末余额取区间最后一笔的期末余额，没有流水时留白**——显示 0 会被读成「余额已经归零」。

**金额带正负号显示**（进账 `+`、扣费 `−`）：流水里的正负是有意义的，一律取绝对值会让「预占」和「预占释放」看起来一模一样。

**两条读法（固定在表格下方）**：
1. 每一笔的「期初余额」就是上一笔的「期末余额」，中间不会跳；
2. 余额只在账户这一层、不分摊到机器人头上，所以每一笔扣费都从同一个余额里出。

**分页每页 20 条**（可切 20 / 50 / 100）：这里**不跟明细表的 10 条一致**——长表一屏 10 行要翻太多次，而客户来这一页往往是「翻到某一天」。

**时间范围跟随页面顶部**，这一页不自带一套范围选择：同一屏上两个范围各说各的，客户不知道哪个才算数。

空状态：**「这段时间没有流水」** / 「{起} ~ {止} 之间没有{充值 / 扣费}记录。换一个时间范围看看。」

### 7.8 页签 5：通知记录

一句话说明（页面副标题）：**「发过哪些提醒、发给了谁、当时余额是多少。」**

**这一页存在的唯一理由是「留下凭证」**：客户说「我没收到提醒」、平台说「提醒过了」，有这一页就都不用争。所以每一行都必须带上**发送结果**与**触发时的余额**——只记一句「已提醒」等于什么都没记。

三个区块：

#### 区块 5.1 提醒规则

| 列 | 内容 |
|---|---|
| 提醒档位 | 余额低于预警值 / 余额已用尽 / 已经欠费 |
| 触发条件 | 第一档写「账面余额低于 ¥5,000.00（可在『余额与额度』页修改）」；后两档写各自的说明 |
| 提醒方式 | 邮箱 / 短信，按客户在「余额与额度」页勾选的方式显示；后两档标「（固定）」 |
| 频率上限 | 每天最多 1 次，最多连发 3 天 |

> **后两档是事实，不是偏好，所以不能关闭**：「余额已用尽」「已经欠费」发生了一定要告诉客户——客户关掉它，等于关掉「电话已经打不出去了」的通知。第一档（预警值）是偏好，这个数客户自己定。
> **三档各自计数**，所以「快用完了」提醒过之后，真的用尽时还会再提醒一次——这两件事对客户不是一件事。
> **同一档每天最多 1 次、最多连发 3 天**：余额长期不足时不被反复打扰；连续 3 天没处理之后不再重复发，下一次真正触发时重新计数。
> **提醒只是通知，不会自动充值**——自动充值意味着平台在客户没同意的情况下扣钱，账务上不能这么做。

#### 区块 5.2 提醒文案预览

按客户勾选的渠道各给一张卡（邮件 / 短信），写出「你会收到什么」，括号里的数按触发时的真实余额填入。

> **邮件与短信的内容一致**，都写明当前余额、预警值，以及余额用尽后会发生什么。
> **短信不含链接**：账务类短信带链接容易被当成诈骗，客户不敢点。
> 文案里出现的是**占位符**（`{账户名}` / `{账面余额}` / `{预警值}`），不是编一条已经发生的提醒——这是「你会收到什么」的说明，不是历史记录。

#### 区块 5.3 提醒记录

| 列 | 内容 |
|---|---|
| 记录号 | 等宽字体 |
| 发送时间 | `2026-09-20 09:12:04` |
| 提醒档位 | 三档之一 |
| 触发时余额 | 触发那一刻的账面余额（加粗） |
| 触发时欠费 | 大于 0 时红色 |
| 提醒方式 | 邮箱 / 短信（带图标） |
| 接收人 | 邮箱地址或脱敏号码 |
| 发送结果 | `已发送` / `发送失败：{原因}`（红绿徽章） |

> **发送失败也要记，且要写失败原因**：只留成功的那些，「客户没收到」这件事永远查不清是谁的问题。
> **「触发时余额」记的是触发那一刻，不是导出时的余额**：事后回看要还原当时的处境。
> **提醒记录不随页面顶部的时间范围变**：它是对账凭证，凭证不能随手点几下就查不到。要按范围取，到「报表导出」页下载「提醒记录」报表。

**演示数据边界（必须诚实）**：`NOTIFY_RECORDS = []`——截至 2026-09-22，余额从 ¥45,000 花到 ¥42,689.74，离预警值 ¥5,000 还差得远，三档一次都没被触达过。**不为让页面好看而编记录**：编出来的是一条伪造的账务事实，客户在验收时无从分辨哪些是真的。所以原型这一页给的是完整表结构 + 规则说明 + 文案预览 + 空状态文案（「还没有发出过提醒」），客户点开就知道「长什么样、什么时候会有一条」，不需要看见假的行。

### 7.9 页签 6：报表导出

一句话说明（页面副标题）：**「把账导出去对账；每一列是什么意思；谁导走过。」**

两件事必须同时做到，缺一样客户就不敢用：**一、每一列是什么、怎么算出来的，写在客户看得见的地方**——对不上账时他得能自己查；**二、每一次导出都留一条记录**——账务数据出域必须有痕，这是审计要求，也是客户内部的合规要求。

四个区块：

#### 区块 6.1 导出说明

四张小卡（`lg:grid-cols-4`）：

| 卡片 | 值 | 说明 |
|---|---|---|
| 导出范围 | `{起} ~ {止}` | 跟随页面顶部的时间范围 |
| 单次上限 | 3 个月 | 更长的区间请分几次导出 |
| 文件格式 | CSV（UTF-8） | 带 BOM，中文用 Excel 打开不乱码 |
| 导出权限 | 计费管理员 | 每次导出都会留下记录 |

> **单次上限 3 个月，且拦在下载之前**：范围超限时不给下载，也不下空文件——让客户下一个和范围对不上的文件，比不让他下更糟。文案要说清「把页面顶部的时间范围收窄到 3 个月以内」或「按季度分几次导出」，只报一句「超过限制」客户不知道怎么改。
> **导出的是「这一刻的账」，与页面上看到的一致**：同一份数据导两次，内容完全相同，与当时翻到第几页、展开了哪一格都无关。
> **金额导出成数字**（如 `42689.74`），不带货币符号与千分位——带逗号的数字在 CSV 里会被切成两列。**时长统一导出成分钟、保留两位小数**。

#### 区块 6.2 报表清单

| 列 | 内容 |
|---|---|
| 报表 | 五张：充值记录 / 扣费记录 / 通话消费明细 / 消费统计 / 提醒记录 |
| 这张表是什么 | 一句话说明 |
| 与页面上哪一块同一份数据 | 如「资金流水 · 充值记录」 |
| 字段数 | 8 / 9 / 9 / 9 / 9 |
| 范围内行数 | 按当前范围实时算；为 0 时写「这段时间没有数据」并**禁用下载** |
| 操作 | 「下载 CSV」 |

> **下载前先看一眼行数**：能避免导出一个空文件还不知道。行数为 0 时禁用下载，而不是下一张只有表头的空表。
> **导出的行与页面是同一份数据**：报表定义复用页面上那一份取数函数，不在导出这条路上另写一套筛选——两套筛选迟早会分叉，客户导出来的账和屏幕上看到的对不上，是最难解释的一种故障。

#### 区块 6.3 字段口径

五列：**字段（也是文件里的表头）/ 单位 / 这是什么 / 口径说明 / 本范围内的一个真实示例**。

**示例取范围内第一行的真实值，不手写**：手写的示例改了字段忘了改，这张口径表就成了一份假文档，而客户是照着它去对账的。

**三条必须写明的口径**：
- 金额字段单位是元、写数字；时长字段单位是分钟、保留两位小数；费率类字段单位是元/分钟。
- **未接通与待定价的通话在「通话时长」「适用费率」「本通费用」三列留空，而不是写 0**——写 0 会被读成「这通免费」，实际是「暂不扣费、定价后补扣」。
- 「扣减来源」写的是这笔钱从哪一个额度批次里扣的，跨批次时标明含几个批次；**先扣快到期的**。

#### 区块 6.4 导出记录（本次会话）

| 列 | 内容 |
|---|---|
| 记录号 | `exp_0001` |
| 导出时刻 | **真实时间**（不是数据截止日） |
| 报表 | 报表名 |
| 时间范围 | `{起} ~ {止}` |
| 行数 / 字段数 | 与下载的文件一致 |
| 操作人 | `{账户名} · 计费管理员` |
| 文件名 | 含账号名、报表名、范围与导出时刻，如 `充值记录_示例科技有限公司_2026-07-01_2026-09-22_20260923_141207.csv` |

> **导出时刻用真实时间**：导出是客户此刻做的事，不是一个演示数据里的日期。页面别处用数据截止日当「今天」，是为了让「本月」落在演示数据里；这里要记的是「这份文件什么时候出去的」，用假日期反而是错的。
> **文件名里不含 `:`**（Windows 文件名不允许），时刻部分写成 `20260923_141207`。
> **原型里这一块只列本次会话内导出的记录，刷新就清空**——原型不连服务端，记录号不做跨会话唯一。正式环境里导出记录长期保留、与「通知记录」一样可回查，否则「谁把客户数据导走了」这个问题永远答不上来。

### 7.10 挂载点：机器人发布流程

**在两处显示单价，都是只读，都不改发布流程本身。**

**（a）基础配置页实时预览** —— `components/bot/BotBasicConfig.tsx`，模型配置区（大模型 / TTS / ASR / 音色）正下方新增一行只读条：

> 当前配置单价：**0.22 元/分钟** ｜ 按此单价，1 万元套餐（含 7500 元映射额度）约可通话 **34,090 分钟** 〔查看计费依据〕

- 改任意一个模型 / 音色后，费率立即重算，不需要保存。
- 未发布过的机器人同样显示（这是「预计发布后的单价」）。

**实现落法**（`components/billing/BotRatePreviewBar.tsx`，挂在模型配置区最后一行，在 ASR 那组输入的下方）：单价**不在这个组件里算**，由机器人表单算一次后作为 `rateResult` 传进来，和发布弹窗共用同一个结果。编辑页自己再调一次计价引擎的话，两处的输入一旦有细微差别（比如一个带了版本号、一个没带），客户就会看到「编辑页 0.39、发布弹窗 0.22」这种当场打脸的场面 —— 守卫测试锁住这条。

「约可通话多少分钟」用套餐的映射额度总额折算，**不在组件里硬编码 7500**：金额从套餐数据取，运营改了套餐，这一句跟着变。
> **这是全站唯一保留折算分钟数的地方**（见 §7.2 的三处作废旧卡）：这里的分钟数就写在单价旁边，答案与依据同一行；面客的余额页与汇总卡一律只给金额口径。

算不出价时（`accuracy: 'pending'`）整条换成 §7.12 的 A3 文案「当前配置暂无价格」，**不显示 0.00 元/分钟，也不给「查看计费依据」的入口** —— 没有价可依据，点进去只能看到一个占位的 0。

**（b）发布弹窗内的确认卡片** —— `components/bot/BotConfigForm.tsx` 的 `isPublishModalOpen` 弹窗，在「版本说明」文本框**上方**插入：

> **本次发布后的通话单价：0.39 元/分钟**
> 相比已发布版本 V1.8（0.22 元/分钟）**上涨 0.17 元/分钟**。
> 原因：大模型由 Gemini Flash 2.0 改为 Gemini Pro 1.5。
> 发布后，新产生的通话将按新单价计费，**已产生的通话费用不变**。

- 「相比已发布版本」这一段只在单价发生变化时出现。
- 首次发布的机器人不显示对比段，只显示单价和一行「这是该机器人首次发布的价格」。

**（c）发布时留痕** —— 点「确认发布」时（`handlePublishVersion`），把费率快照写进机器人配置的 `billingRateSnapshot`。

**类型名是 `BotRateSnapshot`**（`types.ts`），不是设计稿里写的 `BotBillingRateSnapshot` —— 它同时被逐通通话的快照复用，带上「Bot」以外的限定词会让人以为只有机器人级那一份。字段以代码为准，设计稿与实现的差异如下（其余字段同名同义）：

| 设计稿字段 | 实现 | 为什么改 |
|---|---|---|
| `tierLabel: string` | **无此字段** | 档位名由 `tier` 经引擎的 `TIER_LABEL` 查出来。存一份文字进快照，改了叫法就会让老快照带着旧叫法显示出来 |
| `currency: 'CNY'` | **无此字段** | 整个账户只支持人民币，一个恒为 'CNY' 的字段不携带信息 |
| `asrModel` / `ttsModel` / `llmType` / `voiceName` | `asr` / `tts` / `llm` 三个子对象 | 成本要按「用哪个供应商的哪个型号、按什么计价单位」算，平铺成四个字段就没法带上单价和计价单位 |
| `llmOutputPriceMissing` | 成本表里按模型标记 `estimated`，快照不带 | 该标记属于成本参数，不属于这一次计算的结果 |
| （设计稿没有） | `roundingRuleVersion` / `billableBasis` / `minBillableSec` | 取整口径也要留痕，否则改了取整规则就没法把老账按当时的算法复算 |
| （设计稿没有） | `fxUsdCny` | 海外模型按人民币计价，汇率必须一起冻结 |
| （设计稿没有） | `hash` | 配置指纹（不含时刻），用来判断「这两通是不是同一套配置算出来的」；`snapshotId` 由指纹 + 时刻推出 |
| `accuracy` | 不在快照上，在 `BotRateResult` 上（`{accuracy:'priced', rate}` / `{accuracy:'pending', missing, reasons}`） | 算不出价时根本没有快照可存。发布流程据此**不覆盖**旧快照，配置里不会留下一个 0 元单价冒充价格 |

**为什么必须留痕**：通话是按**当时的费率**扣费的，平台后续调价不能改写历史账单。没有这个快照，任何一次调价都会让历史费用变得无法复现。**逐通通话还要再拿一份自己的副本**（`captureSnapshotAt` 逐层复制三个子对象）—— 直接引用机器人级那个共享对象的话，改一行配置就会连带改掉所有历史通话的单价和金额，而账面上什么都看不出来。

2. **反查能顺带回答「这通到底是不是这一通」**。通话记录模块里只有一通有完整详情，其余跳过去会**回落到示例通话**（`detailMatchesRequest`）。回落到示例通话时显示的时长、内容都属于另一通电话，金额必须整块藏起来并说明原因 —— 光看 `billing` 字段有没有值是判断不出这件事的。

第三轮按「客户读这句会怎么理解、会不会去问客服」逐句过了一遍，改了这些。**每一句都对应一个客户会误解的点**，不是润色：

## 8. Requirements

### P0 · Must-Have

> **P0 的边界**：回答三个问题所需的**只读能力**，加上发布侧的单价预览与快照。
> **一屏余额 + 两张表 + 一个明细面板 + 两个挂载点**。任何导出、图表、充值、发票都不在 P0。

#### R1. 导航与路由接入

在侧边栏新增一级菜单「计费中心」，并在 `App.tsx` 的路由中接入页面组件，`bots` 通过 props 传入。

**验收标准**
- [ ] 侧边栏出现「计费中心」菜单项，点击后 `activeMenu` 变为 `'计费中心'`，顶栏标题显示「计费中心」
- [ ] 菜单项排在「监控报表」分组之后、「短信管理」之前
- [ ] 页面能拿到并展示当前 `bots` 里的机器人（至少 2 个演示机器人：`滴滴出行智能客服 (Demo)`、`🤖 语音 Agent 演示 (多工具场景)`）
- [ ] 重复点击、切换到其他菜单再切回，页面状态正常无报错

#### R2. 定价引擎（纯函数 + 成本参数表）

提供一个不依赖 React、不依赖任何 UI 的纯函数，把「机器人配置 + 成本参数表 + 语言参数」映射成费率。

**验收标准（Given / When / Then）**

- Given 成本参数表已加载，When 传入一个 ASR / TTS / LLM 都能在表中找到对应项的机器人配置，Then 返回 `{ accuracy: 'priced', rate }`；`rate` 里带成本合计（`costPerMinMicro`，微元）、报价列表（`priceListMicro`）、适用费率（`priceMilli`，厘）、触底标记（`floorApplied`）、档位（`tier`）与两个版本号（`pricingRuleVersion` / `costTableVersion`）
- Given 成本合计 × 2 小于 0.15，When 计算费率，Then 费率取底价 `priceMilli === 150`（0.15 元/分钟），且 `floorApplied === true`（结果中标记最低价兜底已触发）
- Given 成本合计 × 2 等于 0.1422，When 计算费率，Then 向上取整到 0.01 元后为 0.15，费率 = 150 厘；此时与底价相同，`floorApplied === false`（**只有取整后严格低于底价才算触底**）
- Given 成本合计 × 2 等于 0.3422，When 计算费率，Then `priceMilli === 350`（0.35 元/分钟，向上取整到分）
- Given 成本合计 × 2 恰为整数分（如 0.30），When 计算费率，Then `priceMilli === 300`（取整不引入多余进位）
- Given 计费时长为 0 秒（未接通），When 计算金额，Then `amountCents === 0`（`computeAmountCents(0, priceMilli) === 0`）
- Given 机器人缺 ASR / 音色 / 大模型任一项，或所选模型在成本表里既没有 `boundModelValue` 绑定项、也没有同 `id` 条目，When 计算费率，Then 返回 `{ accuracy: 'pending', missing: [...], reasons: [...] }`，**不抛异常、不返回 0、也不静默套一个默认值**
- Given 同一份配置，When 连续调用两次，Then 返回完全相同的结果（纯函数，无副作用、无 `Date.now()` 参与计算）
- [x] 成本参数表以「版本号 + 生效日期」组织（`COST_TABLE_VERSION = 'cost-2026-01'`，生效日 `2026-01-01`），快照里带上版本号，便于将来复现历史费率
- [ ] 该函数有对应的静态测试，覆盖上述全部分支

#### R3. 账户概览条

**验收标准**
- [ ] 打开计费中心，无需任何点击即可看到「余额」与「可用额度」两个数字，两张卡都标「截至今日」

## 10. Open Questions

> 每一条都需要用户或对应角色拍板。**Blocking = 不回答就无法开工或无法把数字算对**；Non-blocking = 可以在实现过程中解决。
>
> **实现期间的落定与偏离（2026-09-22）**：
> - **Q3（是否展示成本）**：按「不展示」落地。依据面板默认只有模型组合、档位、费率；成本与加价倍率放在默认关闭的「内部视角」里。**客户版上线时这个开关要摘掉**，原型里保留它只是为了给内部评审看算法。
> - **Q7（套餐里的 2500 元）**：原型按「平台与并发服务费，不进余额、不能打电话、不随余额清零」处理，并在「套餐」区块用一列写明 ¥10,000 与 ¥7,500 的差额。第三版进一步定死口径：**1 路 = ¥10,000 套餐 / ¥7,500 映射额度 / ¥2,500 平台与并发服务费；6 路 = ¥60,000 / ¥45,000 / ¥15,000**。真实构成待商务确认。
> - **Q10（余额提示阈值）**：原型里有**两个**阈值，第三版明确它们各管一件事：① 概览条下方的余额不足提示条，按「账面余额 < 映射额度总额的 20%」（`LOW_BALANCE_RATIO = 0.2`）触发，对所有客户一致；② 客户在「余额与额度」页自己设的**预警值**（演示账户用平台默认的 ¥5,000），决定发不发提醒。两者可以不一致。演示数据里余额还剩约九成（¥42,689.74 / ¥45,000）且远高于 ¥5,000，所以提示条与提醒都不会出现——余额够的时候不该吓客户。
> - **Q17（最短计费时长）**：按「不设 60 秒下限」落地，但**每一通接通的电话最低收 0.01 元**（`minBillableSec = 1` + 金额向上取整到分）。未接通不收费。
> - **计费时长列**：本期**没有**单独做「计费时长」列——演示数据里没有转人工分段，`billableSec === durationSec`，多一列永远是同一个数。取整口径已经写进每通快照（`roundingRuleVersion` / `billableBasis` / `minBillableSec`），将来真出现「转人工后不计费」，按快照里的口径就能把新老账分开复算。**这是相对原设计的一处删减，不是遗漏。**

### Blocking

| # | 问题 | Owner | 为什么阻塞 |
|---|---|---|---|
| **Q1** | **「向上取整」取到什么粒度？** 到分（0.01 元）、到 5 分（0.05 元），还是到角（0.1 元）？用户举例「成本 0.15 → 报价 0.30」，0.15×2=0.30 正好是整数，看不出取整粒度；但后文「映射价会从 0.15 涨到 0.3，甚至 0.5」又像是一组固定档位。**我的倾向：取到分（0.01 元）。** 理由：粒度越细，客户越难察觉「被凑整多收」，争议越少；同时和「最低 0.15 元/分钟」的分位口径一致。**（实现已按「到分」落地：`priceGridMilli = 10`，即 10 厘。）** | 产品 / 商务 | 直接决定每一通电话的金额，是定价引擎最核心的参数，且不可事后更改 |
| **Q2** | **「成本 × 2」的 2 倍率对全部模型档位统一吗？** 是否存在协议价客户、大客户折扣、或者高成本模型的倍率更低（避免单价高到卖不动）？**我的倾向：P0 全档统一 2 倍**，折扣进 P2（R24）。 | 商务 | 若存在差异化倍率，定价函数需要多一个参数，且费率档位表要重做 |
| **Q3** | **客户端是否展示成本？** 本 PRD 的处理是「默认只展示档位名 + 模型组合 + 最终费率，成本放在默认关闭的『内部视角』里」。这是我自己定的，需要确认。**我的倾向：坚持不展示成本。** 展示成本等于公开 2 倍加价率，会直接引发「凭什么翻倍」的谈判，且对客户没有任何决策价值 —— 客户要的是可解释性，不是平台的成本结构。 | 产品 / 商务 | 决定计费依据面板的信息架构，也决定 §7.6 的表格列 |
| **Q4** | **千问 / MiniMax 的处理方式确认**：采纳 §6.2 的「内部成本模型映射表」（方案 B），P0 不动现有枚举？还是要求 P0 就把千问 / MiniMax 加进 `ASRModel` / `TTSModel` / `ModelType`？ | 产品 / 研发 | 决定是改 1 个新文件还是改 3 个枚举 + 4 处联动分支，工作量差一倍以上 |

| **Q6** | **转人工之后的时长计费吗？** 本 PRD 的 P0 处理是「不计入 AI 通话费用，单独列一列」。但如果人工坐席要单独计费，就需要在计费中心里多一个计费项（属于 R27 范围）。 | 产品 / 商务 | 决定计费时长列的口径和金额 |
